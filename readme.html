Android Personal Base Platform

A base Android app you extend forever. When you need something new — a frontend for your backend, a webcam server, a stock management system — you build it as an App on this base instead of starting over. The platform already provides capabilities, transport, storage, security and a UI kit, so each App writes only what is genuinely its own.

Vocabulary — three terms, no others

This distinction governs everything. There is no "plugin" category and no fourth kind of thing.

Platform App
The whole application: shell, navigation, page structure, core library. The container for everything.
Frozen — features are never added here
Platform Feature
A capability of the platform itself — the Capabilities API, the security lock. Built directly on the platform.
Pinned · toggle only · never removable
App
A specific thing you build — a webcam server, a backend client, a stock management system.
Extensible forever · any size
The One Rule — we never write code at the platform level. The only code we add is extend a core capability to its full capability. Apps then use those capabilities however they want. This is what keeps the base expandable without forking.

Two kinds of things, with opposite instance rules

Apps — one instance per App

  • Gated by the user's toggle
  • Own state, own lifecycle, own UI
  • Switching one off must not affect another

Capabilities — one shared instance

  • A capability is the device service
  • One camera, one microphone, one manager
  • Every App shares it; none owns a copy
WRONG   App A → own notification manager + port
        App B → own notification manager + port      (duplicate services contending for one)

RIGHT   ┌─ NotificationManager  (single platform instance)
        │   ├─ channel for App A     ← App A posts here
        │   ├─ channel for App B     ← App B posts here
        │   └─ channel for App C     ← App C posts here
The manager is the shared singleton; the channel is the per-App slot. Same for hardware: the camera capability manages the single camera; a webcam App consumes it.

The pages — Apps are the top layer

PagePurposeRules

There is no top-level Capabilities page — capabilities are reached from Settings.

Writing an App

Annotate a class. The registry is generated at build time, so no shell file is ever edited. 

@PlatformAppDefinition(id = "my-app", name = "My App", order = 20)
class MyApp : PlatformApp {

    override val id = "my-app"
    override val name = "My App"
    override val icon = Icons.Default.WavingHand
    override val description = "A minimal App demonstrating the contract."
    override val version = "1.0"

    // State exists only while the user has this App switched on.
    private var greetings = 0

    // Declare what you contribute. Everything here is optional.
    override val contribution = AppContribution(
        dashboardCard    = { scope -> GreetingCard(scope) },
        dashboardActions = listOf(
            DashboardAction(id = "greet", label = "Say hello", onInvoke = { greetings++ })
        ),
        settingsSection  = { scope -> /* your settings UI */ }
    )

    // Your own full screen, opened by tapping your card.
    @Composable
    override fun AppContent(scope: AppScope, onBack: () -> Unit) { /* … */ }
}
That is the whole integration. The App now appears on the Apps page with its toggle, its card renders on the dashboard, and its logs flow to the Logs page.

Exposing a capability as a server

class WebcamApp : PlatformApp,
                  CapabilityServingApp {

    override fun httpPayload(): String =
        """{"streaming":true,"clients":$clients}"""

    override val servePath: String get() = "camera"
}
The route is bound to the App's live instance, so a stopped App serves nothing.

App lifecycle and the safety toggle

  • The user holds sole control — nothing can force an App on
  • Toggle appears on the App's entry in the Apps page
  • Off → inert. No instance, nothing executes, state cleared — a full teardown
  • On → instance created, it runs, contributes what it declared
  • The platform remembers toggle state; it survives restarts
  • When off, the card stays but reads as disabled
Rationale: the user must always be able to completely stop any App on the device.

One instance, many views

user toggles App ON → one instance
                        ├─ dashboard card       (a view onto it)
                        ├─ the App's own screen (a view onto it)
                        └─ settings section     (a view onto it)
Never two instances. The card and the full screen read the same live state — this is what makes the abstraction real rather than nominal.

Pinned platform surfaces

Fixed, toggle-only, cannot be moved or hidden.

Capabilities API — one surface exposing every device capability, with a master on/off and per-capability on/off. Every capability is always listed; anything unusable is greyed out with the reason shown, never omitted. Also served at /api/capabilities.
Security lock — biometric unlock with a user-configurable inactivity policy, from immediate to one hour. The lock sits ahead of every App surface; no App toggle can bypass it.

Dependencies run one way: :app → :core + :apps, and :apps → :core only. A :core or :apps reference to shell code is a compile error, not a convention.

An App here is a feature you write, not software you install.

There is no per-App install step, and Apps are never downloaded or loaded at runtime. Adding an App means rebuilding. Shipping Apps that install independently at runtime would be a different, much larger capability this design does not attempt.

Invariants — these must never break

  • No feature code on the platform. Apps live in Apps; capabilities are completed in core.
  • One instance per enabled App. Disabled → no instance, no execution, state cleared.
  • Capabilities are shared, never duplicated per App.
  • Logs are a compulsory one-way sink.
  • Every App appears on the Apps page with a working toggle the user alone controls.
  • The Dashboard starts empty, and the user controls hiding and ordering.
  • Apps are not forced to use the dashboard or the settings.
  • Adding an App never requires editing the shell.
  • Platform settings and App settings are distinct.
  • An App's size is unconstrained.

Security

  • Signed commands — HMAC-SHA256 over the command fields
  • Anti-replay window — commands outside the TTL are rejected
  • RBAC — GUEST, AUTHENTICATED, ADMIN gate sensitive hardware
  • Safe facade — Apps reach capabilities via PlatformContext, never raw Android APIs
The embedded server currently runs without authentication. Treat it as a development surface — do not expose it to an untrusted network.

./gradlew :core:testDebugUnitTest  # core only
